# 编辑保存：更新原作 / 另存副本 设计决策

> 迭代日期：2026-10-07
> 关联：`2026-10-05-voice-meme-studio-design.md`

## 需求

1. 编辑已有作品时，用户可选择**更新原作**（保留原 `id` 与创建时间）或**另存副本**（新身份，与原作独立修改、删除）。
2. 作品记录创建时间 `createdAt`，并记录最近修改时间 `updatedAt`；排序按最近修改时间（旧记录没有该字段时回退到创建时间，**绝不回填、不伪造**）。
3. 保存链路拆成三段：封面渲染 → 写入 IndexedDB → 回显/刷新作品集。前段失败不得宣布成功；写入成功但回显（`get`）或列表刷新（`list`）失败时，用户能核对真实结果，**不需要、也不应该再点一次保存**。
4. 同一次保存的重试必须幂等（不产生第二个副本）；用户明确"再另存一份"必须产生新身份。同名作品允许并存，标题不作为唯一键。

## 关键决策

### 决策 1：副本身份在编辑器会话内**提前确定**（预占 id），而不是写入成功后才生成

- 进入"另存副本"保存时，先在内存中生成并持有新 id（`reservedCopyId`），此后无论渲染重试、写入重试、回显失败后核对，都复用同一 id。IndexedDB 的 `put` 按主键覆盖，重试天然幂等。
- 预占只在保存尝试开始（渲染成功、构建记录）时发生；渲染失败不预占。
- 预占身份仅存于 `useStudio` 的内存状态：本应用刷新后只恢复已保存作品、不恢复未保存草稿（见总设计"状态与数据流"，避免用户不知情时持久化声音），因此身份的生命周期与编辑会话一致即可。
- 确认提交成功后，草稿"过继"为该副本（`draft.id = 副本 id`），并清除预占。此时再点"另存副本"会预占**新的** id——这就是"同次重试"与"另建一份"的分界：确认提交（或切换/新建/编辑其他作品）是身份边界，未确认前的所有点击都是同一次。

### 决策 2：保存完成状态由"存储中的记录"持有，UI 只持有**未确认态**

- 唯一事实来源是 IndexedDB。写入后用**点读 `get(id)` 核对 `updatedAt` 令牌**（read-your-writes），而不是依赖 `put` 的 Promise 就宣布成功，也不靠重拉整个列表来判断是否写入。
- UI 侧只保留一个 `unverifiedSave { mode, id, token, meme }`：
  - `get` 命中且 `updatedAt === token` → 确认成功，清除未确认态，本地同步该条记录，再尝试刷新列表。
  - `get` 失败（事务/存储瞬断）→ 保持未确认态，提供「核对保存结果」；写入其实已成功时，核对后直接进入作品集，**不重复写入**。
  - `get` 未命中/令牌过期 → 提示可能未写入，保留编辑内容，用户可重新保存（同 id 覆盖，仍不会产生副本）。
- `list` 刷新失败与"写入是否成功"彻底解耦：点读已确认时，本地先把该条并入 `collection`，再标记 `listStale` 并在作品集提供「重试刷新」。用户不会因为列表刷新失败而被迫重存。

### 决策 3：时间戳由核心层纯函数生成，写入路径集中

- `createMeme(id, content, now)`：新作品/副本，`createdAt = updatedAt = now`。
- `reviseMeme({id, createdAt}, content, now)`：更新原作，身份与创建时间原样保留，只换内容与 `updatedAt`。
- `copyMeme(source, newId, content, now)`：语义化封装，副本是创建时刻为 `now` 的全新独立作品；源作品的 `updatedAt` 不变。
- 旧记录 `updatedAt` 为 `undefined`：`sortMemes` 用 `updatedAt ?? createdAt` 排序，读取路径永不写回该字段；界面只显示"创建于 …"，不显示修改时间。

## 方案对比

| 方案 | 副本如何不重复 | 写入后回显失败 | 评价 |
|---|---|---|---|
| A. 写入成功后才生成 id（现状变体） | 无法保证：成功与否不确定时，重试必然再 `put` 一条新记录 | 只能让用户再点保存 → 重复副本 | 否决，正是要修的问题 |
| B. 会话内**提前确定身份** + 幂等 `put` + 点读核对（采用） | 未确认前复用预占 id，`put` 覆盖同一主键 | `get(id)` 核对令牌，确认则不重写；列表失败仅标记 `listStale` | 与现有 IndexedDB 主键语义完全契合，无需新表，测试可替身驱动 |
| C. **持久化保存意图表**（pending-intent store） | 意图先落库带客户端去重键，提交后标记完成，刷新后可恢复 | 重开页面可恢复未确认意图并继续核对 | 对"刷新恢复未完成保存"的产品才有必要；本产品明确不持久化未保存声音，意图表会提前写入 Blob、违背该原则，且多一套存储/迁移/清理成本，本期否决 |
| D. 只靠 `put` resolve 即成功 + 捕获错误后让用户选择"重试/放弃" | 用户承担判断，极易选错 | 无法区分"已写入但回显失败" | 否决，把不确定性转嫁给用户 |
| E. 用标题作幂等键/拒绝同名 | 标题相同即覆盖 | —— | 否决：用户需要同名并存，且会误覆盖原作 |

方案 B 与 C 的取舍本质：**身份要多早确定、保存意图要活多久**。本产品意图的生命周期 = 编辑会话（内存），刷新即放弃未保存内容是既定隐私边界，因此 B 足够且正确；若未来要求"刷新后仍可完成上次保存"，再升级为 C（新增意图仓储，`useStudio` 的未确认态改为可持久化结构，调用点不变）。

## 防重复副本 / 防误覆盖的具体保证

- 更新原作：`reviseMeme` 固定使用原 id，UI 上该路径不会出现新 id；副本路径固定不使用原 id。两条路径在构建记录时就分流，不依赖事后判断。
- 另存副本：确认前 `reservedCopyId` 恒定；确认后草稿过继给副本并清预占，"再另存一份"才生成新 id。
- 写入重试（`put` 失败后再点、或核对发现未命中后重存）：同一 id 幂等覆盖，记录数不增加。
- 独立生命周期：副本与原作是两条主键不同的记录，删除/重命名其中一条不影响另一条；`rename` 也只动本记录并刷新自己的 `updatedAt`。
- 渲染失败：发生在构建任何身份与写入之前，仅报错并保留草稿。
- 成功宣布时机：只有 `get(id)` 令牌核对通过才进入作品集并提示成功；`list` 失败不回滚成功态，只提示列表待刷新。
